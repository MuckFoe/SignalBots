Chore Bot LLM Assist

A local language model on the Mac mini translates free-text messages into the chore bot's commands. The model only reads and suggests: the bot validates everything with its own parsers and makes every change itself.

01What it is

Today the chore bot only understands exact commands like erledigt Bad putzen or aufgabe Fenster jeden Montag. Anything else gets a "Meintest du …?" guess or silence. The LLM assist adds three things:

  1. Free text to command. "Bad ist sauber" becomes erledigt Bad putzen, after a short yes/no check.
  2. Shortcut through dialogues. If a message already contains the details a multi-step interview would ask for, those steps are skipped. "Erinner uns jeden Montag um 8 ans Fensterputzen, jemand muss es bestätigen" creates the chore after one "ja" instead of five questions.
  3. Helpful fallback. If the bot still can't tell what someone wants, it replies with a short list of commands. Normal group chatter stays unanswered.

Only the chore bot (HouseChoreTracker/) uses it. The router, expense bot and rental bot are untouched.

The one rule everything follows The LLM turns a sentence into a small JSON object (an intent plus slots). It never writes to the database and never chooses what happens next. Every slot goes through the parser the bot already uses for that value, and every change runs through the same functions as the typed commands.

02Architecture

Nothing about the existing message path changes. The chore bot gets one extra outgoing HTTP call over the LAN to the Mac mini, made only for messages the normal parsers didn't understand.

03Message pipeline

Every message goes through handle_command() in commands.py, which tries deterministic parsers from top to bottom. The LLM hooks in at three points: a yes/no check at the very top, inside the chore-creation interview when an answer is rejected, and at the very end when nothing matched.

04What the bot does with an answer

The model always answers with the same JSON shape. kind says whether the message is a request (action), a request the model couldn't decode (unclear), or people talking (chatter).

{
  "kind": "action",              // action | unclear | chatter
  "intent": "add_chore",
  "slots": {
    "name": "Fensterputzen",
    "schedule": "every monday",  // checked by parse_schedule()
    "remind_time": "08:00",      // checked by parse_reminder_time_answer()
    "done_confirmation": true,
    "chore": null, "field": null, "value": null, …  // every slot key, null if unused
  },
  "suggestions": [],
  "confidence": 0.9
}

Slot formats the prompt asks for

The prompt tells the model to write values in the exact phrases the bot's parsers already accept. That way the model does the language work ("jeden zweiten Montag morgens") and the parser does the strict work.

SlotAccepted valuesExample input → slot
schedule (recurring)every day, every 2 weeks, every monday, every 3 months, none"alle zwei Wochen" → every 2 weeks
schedule (one-time)today, tomorrow, friday, 3 days"übermorgen" → 2 days
remind_timeHH:MM or anytime; morning 08:00, noon 12:00, evening 19:00"abends" → 19:00

when / durationnow, 1 week, 5 days"ab nächster Woche 2 Wochen" → 1 week / 2 weeks

The bot has no "every 2nd Monday" schedule. A weekday schedule is always weekly, so "jeden zweiten Montag" becomes every 2 weeks.

06Interview shortcut

Creating a chore by hand is a five-step interview stored in the pending_chore_setups table. The LLM doesn't build a parallel flow. It writes the details it found into that same row and sets step to the first missing one. From there the existing, tested dialogue code takes over unchanged, including cancel, stale-dialogue handling and the final create.

Help in the middle of an interview

If someone is in the interview and their answer doesn't fit the current step (today that gives a "So geht's: …" hint), the answer goes to the LLM together with what's already known and which step is being asked. "jeden Montag früh" at the schedule step fills schedule and remind_time together and jumps straight to the confirmation question. If the model can't fill the asked-for step, the usual hint is shown. abbrechen and anything the step parser already understands never go to the LLM.

07The yes/no check

Any change the LLM proposes waits for one confirmation from the person who wrote the message. This guards against the one failure mode that hurts: a wrong guess that silently changes data.

09Safety model

Read-only

show runs at once with an "understood as" hint. Worst case: the wrong list is shown.

Data-changing

add, once, done, undo, edit, rename, name, vacation. Yes/no if complete, otherwise the normal interview.

Destructive

delete_chore only opens the edit dialogue's delete step, which asks its own question. The direct lösche command is never used.

Not reachable

Admin, reset group, language, timezone. Not in the intent list, and an unknown intent is thrown away by the parser.

  • Execution always goes through the same functions as typed commands, so admin checks, "gibt es schon" and "nicht gefunden" behave identically.
  • The LLM output is limited by a JSON schema, and parse_output() rejects anything that doesn't fit: unknown kind, unknown intent, an action without an intent.
  • Fail open: no answer within 8 s, a connection error, an HTTP error or broken JSON all give today's reply.
  • Ollama has no authentication. It must only be reachable from the bot VM (firewall on the Mac mini, LAN only).

10Decisions and why

Click a decision to read the reasoning and the alternative that was rejected.

A narrow translator, not an agentOne message in, one JSON object out. The bot decides what happens.

An agent setup (tool calling, or MCP) lets the model choose which tools to call and when, often in a loop. That's the "chatbot in the group" behaviour we want to avoid, and it's harder to guard: you need rules against wrong or repeated calls.

With a fixed schema, the worst the model can do is produce a wrong JSON object, which then has to pass the parsers and a yes/no check.

Rejected: MCP server over the bots' /internal endpoints. It would make sense later for a general assistant ("who skipped most chores last month?"), not for command translation.

Validate every slot with the existing parsersThe model normalises language; the parser decides if the value is valid.

The parsers (parse_schedule, parse_reminder_time_answer, parse_duration …) are already tested and define what the bot can store. If the model writes "every 2nd Monday", the parser rejects it, the slot counts as missing, and the user is asked. A bad guess becomes a question, never a wrong value in the database.

Rejected: letting the model produce the storage format directly. That's a second source of truth that drifts from the parser.

Prefill the existing interviewsWrite found slots into pending_chore_setups and jump to the first gap.

The interview code already handles cancel, stale dialogues, step order and the final create. Reusing it means the LLM path can't get these wrong, and there's nothing new to maintain. The table needed no schema change, since every slot already has a column.

Rejected: a separate LLM-driven dialogue. It would duplicate the step logic and behave subtly differently.

Ask yes/no before every data changeDecided on 2026-11-07, from day one of the trial run.

A misunderstood "done" or a chore created with the wrong schedule is annoying and erodes trust in the bot. One extra "ja" is cheap. The question is tied to the sender and dropped by any other message, so it never blocks the group.

Read-only show skips it, since showing the wrong list does no harm. Answers inside an interview skip it too, since they are explicit.

Possible later: skip the check above a high confidence once the log shows the model is reliable.

Execute through the typed command, then show itAfter "ja", run e.g. "erledigt Bad putzen" and add "Tipp: nächstes Mal einfach: …".

Running the real command text guarantees identical behaviour, including the "what's your name?" prompt on the first done. The tip teaches the group the fast way, so over time fewer messages need the LLM at all.

Adding a chore, editing and vacation call the same functions the dialogues call (_finalize_chore_creation, the edit dialogue step, _start_vacation_from_plan), because the command text can't express every option.

Every unmatched group message goes to the LLMDecided on 2026-11-07, with group chatter strictly filtered.

People rarely address the bot by name, so filtering by "@bot" would miss most requests. Instead the prompt says that when in doubt, a message is chatter. Groups get a reply only for action/unclear at confidence ≥ LLM_GROUP_MIN_CONFIDENCE (0.6). The eval measures how often chatter gets a reply, and the target is ≈ 0 %.

If chatter still gets answered: raise the threshold, then add more chatter examples to the prompt.

Local model on the Mac mini, native macOSOllama as a LAN service, not a Proxmox node, not a cloud API.

Group messages stay in the house. On macOS, Ollama uses the Apple GPU (Metal) and unified memory, so a 14B model answers in about 1–3 s. Proxmox can't run on Apple Silicon (ARM), and a Linux VM would fall back to the CPU and be several times slower. A 2-node Proxmox cluster would also have quorum problems.

Connect by fixed IP (DHCP reservation), because mDNS names like macmini.local are unreliable from inside Docker.

OpenAI-compatible API with a JSON schemaPOST /v1/chat/completions, response_format = json_schema, temperature 0.

Ollama, LM Studio, llama.cpp and MLX all speak this API, so the backend can change without touching the code. A JSON schema makes the server constrain the output so it always parses. Small models are much more reliable at constrained JSON than at tool calling.

If a backend rejects the strict schema (HTTP 400), the client retries once in plain json_object mode. The prompt still describes the format.

Fail open, off by default, per-group allowlistLLM_ENABLED=false by default; LLM_SCOPES limits it to the test group.

The bot must never get worse because the Mac mini is asleep. Every failure path returns exactly today's reply, and an 8 s timeout keeps well under the router's 30 s limit. The allowlist lets you try it in one group without touching the others, and turning it off is one env var.

Log every LLM call during the trial runDecided on 2026-11-07: llm_log keeps text, raw output, outcome and latency.

Misses in real use are the best eval cases. export_llm_log.py --jsonl turns log rows into eval-case skeletons. Keep the log as long as testing needs; there's no announcement in the groups (also decided on 2026-11-07). The log moves with a group if its scope id migrates.

Lazy import of requestsllm_assist.py imports requests inside the call.

The bot and its tests load even where requests isn't installed. The container has it via requirements.txt, so no new dependency was added.

16Known limits

  • Mid-interview LLM help covers the chore-creation interview only. The edit and vacation dialogues are prefilled but not helped mid-way.
  • The interview's name step never goes to the LLM, because any text is a valid name.
  • If the message says "must be confirmed" but an earlier step is missing, the interview still asks the confirmation question at the end, because pending_chore_setups has no column for it.
  • "Done by someone else" (erledigt X für Anna) isn't an LLM slot yet. Typing the command still works.
  • The vacation dialogue stores the start delay in whole days, so "in 3 hours" rounds down.
  • Each unmatched message costs one LLM call of about 1–3 s. With a few busy groups that's fine. With many groups, consider an "@bot" filter.
